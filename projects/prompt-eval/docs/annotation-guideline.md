# 要約(summary)の採点ガイドライン v1(2026-08-14)

人手評価の採点基準。judge のプロンプトはこのガイドラインから導く(v3 以降)。
基準を変えるときはこのファイルの版を上げ、どの版で採点したかを記録に残す。

## 用途の定義(すべての判断の前提)

summary は**問い合わせ一覧画面でのトリアージ用**。category / urgency / name / company と
並んで表示され、「何の機能の、どういう件か」を特定するためのもの。
**この要約だけを見て対応作業が行われることは想定しない**(その用途が必要になったら、
要約に詰めるのではなく required_action 等のフィールド追加として仕様から見直す)。

初回の人手評価(run 20260814-103026)で採点がブレた原因は、この用途が
未定義だったことにある。評価基準は用途から導かれる。

## 採点(3 段階)

- **3** … 何の機能・操作の、どういう件かが正しく伝わり、このまま一覧に載せられる
- **2** … 対象は合っているが手直しがほしい(下記「減点する」参照)
- **1** … 要件そのものを取り違えている、主要件を外している、
  または原文に無い情報を含む(推測・創作)

## 減点しない(別項目・仕様で担保されるため)

- 期限・緊急度・影響範囲の省略 — urgency が別項目にある
- 差出人・会社名の省略 — name / company が別項目にある
- 「対応してほしい」「直してほしい」等の定型的な要望の省略 —
  不具合報告・質問において対応要望は自明
- 感情・不満のトーンの省略 — 件名の特定には不要
- 複数要件のうち副次的な要件の省略 — 1 文・50 字の仕様上すべては入らない。
  主要件の選択が正しいことを評価する
- 挨拶・謝辞を削ぎ落としたこと — むしろ望ましい

## 減点する

**2 にするもの:**

- 聞かれている内容の取り違え(例: 置き場所を聞かれているのに「有無を知りたい」)
- **問い・依頼が要件の中心なのに、状況説明だけの要約になっている**
  (例: 上限緩和の可否を聞かれているのに「作業が停止している」とだけ要約する。
  定型的な対応要望の省略とは区別する — こちらは要件の種類が変わって見える)
- 日本語として不自然で手直しがほしい

**1 にするもの:**

- 要件・主要件の取り違え、原文に無い情報の混入(推測・創作)
