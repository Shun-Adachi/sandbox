# prompt-eval

## 概要

プロンプトの版を、正解ラベル付きの評価データセットで採点するハーネス。
llm-api テーマの構造化抽出エンドポイント(`POST /v1/extract`)を評価対象として、
プロンプト 3 版(v1/v2/v3)× 24 ケースのマトリクスを実測した。

llm-api 側で 3 ケースの手動比較に留まっていた「プロンプトをどう直したら
どれだけ良くなったか」を、件数を増やして数字で言えるようにするのがこのテーマの目的。

## 他テーマへの依存

このテーマは例外的に llm-api に依存する。仕組みと範囲は次の通り。

- **依存先**: llm-api(評価対象として)
- **仕組み**: HTTP のみ。`POST /v1/extract` を `--target`(既定 `http://localhost:8100`)に
  向けて呼ぶ。コードの import や相対パスでのファイル参照は無い
- **影響範囲**: `run`(収集)コマンドだけ。テスト 27 件と `score`(採点・レポート生成)は
  llm-api なしで動く
- 契約(`POST /v1/extract` のリクエスト/レスポンス形式)さえ満たせば、
  ステージング環境や別実装にも `--target` で向けられる

## 技術スタック

- Python 3.13 / httpx(評価対象 API の呼び出し)/ Pydantic v2
- OpenAI API(gpt-4o-mini、LLM-as-judge でのみ使用)
- pytest(32 件、OpenAI も llm-api も呼ばずに通る)

## 動かし方

評価対象として llm-api を先に起動しておく(起動方法は `projects/llm-api/README.md`)。

```bash
cd projects/prompt-eval

python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
cp .env.example .env        # LLM-as-judge を使う場合のみ OPENAI_API_KEY を書く

# 収集: 24 ケース × 3 版を呼び、生の応答を runs/<run_id>/ に保存(課金はここだけ)
.venv/bin/prompt-eval run --versions v1 v2 v3

# 採点: 保存済みの応答を採点し、runs/<run_id>/report.md を生成(何度でも無料)
# --judge-prompt で judge の版を選ぶ(人手評価で検証済みの採用版は v5)
.venv/bin/prompt-eval score latest --judge --judge-prompt v5

# 人手評価: 要約 72 件を、版を伏せてシャッフルした CSV に書き出す
.venv/bin/prompt-eval review-sheet latest
#   → runs/<run_id>/review-sheet.csv の human_score 列を 1〜3 で記入する
#     (1=使えない / 2=要手直し / 3=このまま使える。judge と同じ基準)

# 記入済みシートを取り込み、人と judge の一致率・Cohen's κ・不一致一覧を出す
.venv/bin/prompt-eval agreement latest
```

テストはネットワークを使わないので、キーが無くても通る。

```bash
.venv/bin/python -m pytest -q
```

## 評価作業の流れ

このハーネスが想定している改善ループ。1 周が「収集 $0.008・数分」で回る。

```
正解ラベル付きデータセット(24 ケース + 類型タグ)
        │
        ▼
run … ケース × 版のマトリクスで API を呼び、生応答を保存
        │
        ▼
score … 3 層で採点してレポート生成
        ├─ 完全一致: name / company / category / urgency
        ├─ ルール:   要約 50 字以内・必須キーワード
        └─ LLM-as-judge: 要約の質(要件の取り違え・挨拶の混入)
        │
        ▼
review-sheet → 人が採点 → agreement … 人手評価と judge を突き合わせる
        (評価の正は人手評価。judge は一致を確認できて初めて件数をさばく道具になる)
        │
        ▼
レポートで原因を絞る(urgency 混同行列・タグ別一致率・誤答一覧)
        │
        ▼
プロンプトの次版を作る → run からやり直して差分を見る
```

## 実測結果(2026-08-14、詳細は docs/report-2026-08-14.md)

| 版 | 全項目一致 | urgency | category | 要約: 人手平均 | 要約: judge v5 平均 | コスト |
| --- | --- | --- | --- | --- | --- | --- |
| v1(Dify と同じ指示文) | 46% (11/24) | 58% | 79% | 2.92 | 2.92 | $0.006 |
| v2(基準を明文化) | 62% (15/24) | 83% | 83% | 2.92 | 2.92 | $0.006 |
| v3(v2 + 例示 3 件) | 71% (17/24) | 79% | 92% | 2.88 | 2.92 | $0.008 |

- **llm-api の 3 ケース比較で見えた傾向は、24 ケースでも維持された**(46% → 62% → 71%)。
  ただし v3 でも 71% で、例示だけでは頭打ちになることも同時に分かった。
- **v1 の誤りはほぼ「緊急度が一段上に寄る」**。混同行列で 低→中 が 6 件、中→高 が 3 件。
  基準を明文化した v2 でこの上振れはほぼ解消した。
- **v2 → v3 で urgency は 83% → 79% と微退行**。例示は狙っていた類型
  (回避策あり・推測誘発)を直した一方、例示に無い類型(解約 + 今月末期限)を
  低側に引きずった。「直したら別が壊れる」を検出できることが、
  少数ケースの手動確認ではなくデータセットで評価する理由そのもの。
- **3 版とも落とす残課題が特定できた**: 「至急」と連呼するだけの質問(c16)、
  質問だが期限が 24 時間以内(c17)、感情的な口調(c15)、規約上は仕様通りの
  エラーを不具合と分類(c24)。次版(v4)はここを狙って直せばよい。
- **judge は要約の系統的な弱点を出した**: 期限・背景情報の欠落が全版に共通
  (50 字制約とのトレードオフ)。完全一致では測れない品質の劣化を別レイヤーで拾えた。
  ただし judge 平均の数字は人手評価との検証で覆った(次節)。

## 人手評価による judge の検証(2026-08-14)

要約 72 件を、版を伏せてシャッフルしたレビューシートで人が採点し、judge と突き合わせた。
検証は 2 段階になった。初回の採点で人の判断自体に境界事例が見つかり
(「修正してほしい」の省略を許容するか等)、原因は**要約の用途が未定義**だったこと。
用途を「一覧でのトリアージ用(期限・緊急度・差出人は別フィールドで担保)」と定義して
採点ガイドライン(`docs/annotation-guideline.md`)を作り、影響する 11 件を再採点した上で
judge を反復した。

| 人の採点基準 | judge | 完全一致 | Cohen's κ | 結果 |
| --- | --- | --- | --- | --- |
| 初回(用途未定義) | v1 | 75% (54/72) | 0.38 | 期限・緊急度の欠落を過剰減点 / 取り違えを見逃す |
| 初回(用途未定義) | v2(ズレを明文化) | 65% (47/72) | 0.30 | 省略全般を「要望の欠落」に読み替え悪化 |
| ガイドライン v1 | v1(再計算) | 74% (53/72) | 0.23 | 基準を固めた分、v1 のズレがより顕在化 |
| ガイドライン v1 | v3(ガイドライン準拠) | 72% (52/72) | 0.26 | 「問いの中心の脱落」が新たな万能減点に |
| ガイドライン v1 | v4(= v3 + gpt-4o) | 93% (67/72) | 0.67 | 実質的一致。ボトルネックはモデル能力と判明 |
| ガイドライン v1 | v4 の再実行(同一条件) | 97% (70/72) | 0.84 | temperature 0 でも judge は run 間でブレる |
| ガイドライン v1 | **v5(v4 + 要件なしルール)** | **99% (71/72)** | **0.92** | **採用。ただし数字は in-sample の参考値** |

分かったこと:

- **評価基準は用途から導かれる**。人の採点がブレた箇所も judge の失敗も、
  根は「要約が何に使われるか」の未定義だった。仕様を決めたら人の採点は安定し
  (2 は 18 件 → 7 件)、judge を寄せる目標も明確になった。
- **ルーブリックの改善だけでは judge は人に寄らなかった**。gpt-4o-mini は
  v1〜v3 のどの書き方でも「減点パターンを 1 つ掴んで乱用する」挙動を示し
  (κ 0.23〜0.30)、禁止事項の列挙や例示でも直らなかった。
- **ボトルネックは判定モデルの能力だった**。同一ルーブリックのままモデルを
  gpt-4o に上げた v4 で κ 0.26 → 0.67 に跳ねた。judge のコストは
  1 run 約 $0.01 → 約 $0.1 に上がるが、使えない judge は何回回しても無駄なので安い。
- **検証前の judge の数字は実際に誤導していた**。judge(mini)は「v3 の要約が最良」と
  出していたが、人の採点では 3 版ほぼ横ばい(2.92 / 2.92 / 2.88)。
  プロンプト改版は 4 項目の精度を大きく上げた一方、要約の質は変えていない。
- **v4 の残不一致 5 件中 3 件は「お礼のみで要件が無い問い合わせ(c22)」の採点が
  ガイドライン未定義だったこと**が原因。人の採点(その旨が伝われば 3)を根拠に
  ガイドラインの判定記録に確定し、judge v5 に反映した。これは評価セットに合わせた
  調整ではなく仕様の欠落修正だが、**効果測定は同じ 72 件に対して行っているため
  v5 の κ 0.92 は in-sample の参考値**。真の検証はケースを増やしてから行う。
  残る不一致は 1 件(c06 の「有無 vs どこにあるか」の取り違え見逃し)。
- **judge は temperature 0 でも run 間でブレる**。同一プロンプト・同一入力の v4 を
  2 回実行して κ 0.67 と 0.84 だった。72 件程度の n では 1 回の κ に幅があるので、
  判定モデルや基準の優劣を 1 run の κ の小差で論じてはいけない
  (v3→v4 のような大差だけを根拠にする)。

## 工夫した点・設計判断

- **収集(run)と採点(score)を分離した**。課金と時間がかかるのは API 呼び出しだけ
  なので、生の応答を `runs/<run_id>/` にそのまま保存し、採点基準やレポートの
  変更は保存済みデータに対して何度でも無料でやり直せるようにした。
  実務では採点ロジックの試行錯誤の回数が収集よりずっと多い。

- **評価対象をコードではなく HTTP API として叩く**。プロンプトの読み込みや
  モデル呼び出しの実装に依存しないので、同じハーネスをそのまま
  ステージング環境や別実装(Dify 版)にも向けられる。llm-api 側が応答に
  `prompt_version` / `usage` / `latency_ms` を含めているため、
  評価に必要な条件記録が API 契約だけで揃う。

- **正解ラベルには根拠(note)と類型タグを付けた**。ラベルの正しさ自体は
  ハーネスでは保証できないので、「なぜこの正解か」を各ケースに書き残し、
  異議が出たときに議論できるようにした。タグはレポートの分析軸になり、
  「どの類型で落ちているか」から次の修正対象を絞れる。

- **採点を 3 層に分けた**。正解が一意に決まる項目は完全一致、機械判定できる
  制約はルール、自由文の質だけを LLM-as-judge に回す。判定できるものまで
  judge に聞くと、ブレる上に減点理由が追えなくなる。

- **評価の正は人手評価に置き、judge はそれで検証してから使う**。LLM-as-judge の
  採点は「judge がそう思った」以上の裏付けを持たないので、版を伏せてシャッフルした
  レビューシートで人が独立に採点し、一致率と Cohen's κ で judge を検証する
  (シートに版名や judge スコアを載せないのはアンカリングを避けるため)。
  一致が確認できて初めて、judge は人手評価を件数面で代行できる。

- **judge のプロンプトも版付きで管理し、判定を 3 段階に絞った**。judge も
  評価結果を左右する「評価系の一部」なので評価対象と同じ扱いにする。
  5 段階でなく「使える / 要確認 / 使えない」の 3 段階にし、
  reason を score より先に生成させて後付けの採点を防ぐ。

- **API エラーは除外せず不正解として数える**。エラーを分母から外すと
  「失敗の多い版ほど正解率が高く見える」逆転が起きるため。

- **run ディレクトリにケースのスナップショットとデータセットの sha256 を同梱**。
  データセットを後から編集しても、過去の run の採点は当時のケースで再現できる。

- `docs/human-eval-2026-08-14/` — 記入済みレビューシートと対応表(judge 検証の正解データ)
