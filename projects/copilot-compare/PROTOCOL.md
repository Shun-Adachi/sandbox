# 比較の進め方

エージェントを変えても条件が変わらないようにするための手順。
Claude Code と Copilot の両方に、**この文書と `tasks/<課題>/spec.md` だけ**を渡す。

計測は 2 段階に分かれる。

| | 測るもの |
| --- | --- |
| **Phase A** | 仕様書だけを渡した一発勝負で、何点取れるか |
| **Phase B** | 落ちたテストを、どれだけ少ない情報で自力修復できるか |

Phase A は「仕様書の読解力」、Phase B は「対話で直す力」を見る。
どちらも実務で効く一方、混ぜると原因が分からなくなるので分けて測る。

## Phase A — 一発勝負

```bash
python src/new_run.py --agent <エージェント名> --task <課題名>
```

`runs/<エージェント名>/<課題名>/work/` に starter が置かれる。ここが唯一の作業場所。

```
runs/<エージェント名>/<課題名>/
├── work/       ← エージェントに渡す唯一のパス。実装以外を置かない
├── phase_a/    ← Phase A 終了時の凍結。--freeze が作る
└── run.json    ← 計測メタデータ
```

`run.json` と `phase_a/` を `work/` の外に置くのは、**採点側が書いた内容が
エージェントの context に入るのを防ぐため**。以前 `run.json` を作業ディレクトリの中に
置いていたとき、そこに書いた失敗原因の分析が Phase B の開始前にエージェントへ渡り、
ヒント段階の計測が 1 件無効になった。

エージェントへの最初の指示は、毎回この 1 文にする。

> `projects/copilot-compare/tasks/<課題名>/spec.md` の仕様を満たす実装を
> `projects/copilot-compare/runs/<エージェント名>/<課題名>/work/` に書いてください。
> `projects/copilot-compare/PROTOCOL.md` のルールに従ってください。

終わったら `run.json` の `phase_a` に実測値を記入し、採点して**凍結**する。

```bash
python src/score.py --agent <エージェント名> --task <課題名> --freeze
```

`--freeze` は現在の実装を `phase_a/` にコピーする。
これ以降 Phase B で実装を上書きしても、Phase A の点数は残る。
**満点だった場合、Phase B は行わない**（直すものが無い）。

## Phase B — 会話フェーズ

落ちたテストがある場合だけ行う。**ヒントを段階的にしか出さない**のがこのフェーズの肝で、
「どこまで情報を削っても自力で直せるか」を測る。

**Phase A と同じチャットセッションを継続する。** 新規セッションにすると
実装に至った文脈が消え、「自分の書いたコードを直す」ではなく
「他人のコードを読んで直す」に条件が変わってしまう。

| 段階 | 伝えてよいこと |
| --- | --- |
| **L1** | 落ちたテストの**件数だけ**。「テストが N 件落ちています」 |
| **L2** | L1 に加えて、失敗した**テスト名だけ**。中身・期待値は言わない |
| **L3** | L2 に加えて、`pytest` の出力をそのまま貼る |

L1 から始める。エージェントが修正を出したら採点し、満点なら終了。
満点でなければ次の段階へ上げる。**1 つの段階で与える指示は 1 往復まで**。
L3 でも満点に届かなければ、そこで打ち切り、`hint_level` は `null` にする。

```bash
# 各段階のあと、凍結はせずに採点する
python src/score.py --agent <エージェント名> --task <課題名>
```

L1 で使う文面は毎回これに固定する。

> テストが N 件落ちています。仕様書を読み直して直してください。

L2 はこれに次の 1 行を足す。

> 落ちたのは `<テスト名>` です。

L3 は `pytest` の出力をそのまま貼る。加工も要約もしない。

満点に届いた段階を `run.json` の `phase_b.hint_level`（`1` / `2` / `3`）に記録する。
`phase_b.turns` は Phase B で人が指示を出した回数の合計。

## エージェントが守るルール

1. **`tasks/<課題>/tests/` と `tasks/<課題>/reference/` を読まない。**
   採点用の隠しテストと模範解答であり、これを見ると比較が成立しない。
2. 書き換えてよいのは `runs/<エージェント名>/<課題名>/work/` の中だけ。
   `tasks/` 配下、`phase_a/`、`run.json`、他のエージェントの `runs/` は触らない。
3. 追加の依存を入れない。標準ライブラリだけで実装する。
4. 自分でテストを書くのは自由だが、同じディレクトリに置き、
   採点対象のモジュール名（`sse_parser.py` など）と衝突させない。
5. **`pytest` を実行しない。** 採点は人が行う。
   自分で回せると、Phase B のヒント段階（L1〜L3）を飛び越えて
   `pytest` の出力を自力で手に入れられてしまい、計測が成立しない。
6. 依存のインストールをしない。`pip install` は提案も実行もしない。

> リポジトリが公開されているため、1. はエージェントを技術的に縛れない。
> 破られていないかは、採点前に会話ログを見て確認し、
> `run.json` の `used_spec_only` に記録する。ここは正直さに依存した運用になっている。

## 人が守るルール

- **仕様の追加説明をしない。** spec.md が曖昧で詰まったら、それも比較結果のうち。
  質問されたら「spec.md の通りです」と返す。Phase B でも同じ。
- **Phase A の途中で採点結果を渡さない。** 採点は作業が終わったあとの 1 回だけ。
- **Phase B ではヒントの段階を飛ばさない。** 焦って L3 を出すと、
  そのエージェントが L1 で直せたのかどうかが永久に分からなくなる。
- **テスト実行や依存インストールを求められたら断る。** 文面はこれに固定する。

  > テストの実行はこちらで行います。あなたは実行しないでください。
  > 仕様書だけを見て直してください。

  この往復も `turns` に数える。ヒントではないが、人が出した指示ではあるため。
- **原因分析は、そのランの全フェーズが終わるまでどこにも書かない。**
  作業中に分析を書くと、それがエージェントの context に入り得る。
  `run.json` を `work/` の外に出したのはそのためだが、
  ファイル配置だけに頼らず、書くタイミングでも守る。
- **どこで詰まったかを `notes` に残す。** 合格数だけでは、
  同じ点数に至るまでの手数の差も、直し方の質の差も見えない。
  ただし上のとおり、書くのは全フェーズ終了後。

## run.json

```json
{
  "agent": "copilot",
  "model": "claude-sonnet-4.6",
  "mode": "agent",
  "used_spec_only": true,
  "phase_a": { "minutes": 12, "turns": 1 },
  "phase_b": { "minutes": 4, "turns": 2, "hint_level": 2 },
  "notes": "チャンク境界の \\r\\n を最初は取りこぼした"
}
```

| キー | 内容 |
| --- | --- |
| `model` | 実際に使ったモデル名。auto ルーティングなら選ばれた種別も書く |
| `mode` | `agent` / `ask` / `edit` / `cli` など、使った動作モード |
| `used_spec_only` | `tests/` と `reference/` を見ずに済んだか |
| `phase_a.minutes` / `.turns` | 最初の指示から実装完了までの実測分と、指示回数（通常 1） |
| `phase_b.minutes` / `.turns` | 会話フェーズに要した分と、人が指示を出した回数 |
| `phase_b.hint_level` | 満点に届いた段階（`1` / `2` / `3`）。届かなければ `null` |
| `notes` | 詰まった箇所・気づいたこと |

Phase A が満点なら `phase_b` は全て `null` のままにする。

`minutes` と `turns` は自己申告で、厳密な指標ではない。
合格数の差が小さいときに「どちらが手間だったか」を思い出すための記録として使う。
一方 `hint_level` は手順が固定されているぶん、比較に使える。

## 課題を足すとき

```
tasks/<課題名>/
├── spec.md           # エージェントに渡す唯一の仕様
├── starter/          # 空のシグネチャだけ。new_run.py がここを複製する
├── tests/            # 採点用。エージェントには見せない
└── reference/        # 参照実装。ハーネスの自己検証用
```

`src/score.py --reference` が参照実装で全通しすること、
starter が 0 点になることの両方を確かめてから、課題として使う。
